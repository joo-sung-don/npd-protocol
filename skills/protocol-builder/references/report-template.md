# 개발 계획 보고서 템플릿 (1~2쪽)

프로토콜 본문(0~7장)을 **결정하는 사람용으로 줄인 문서**다. 대표, 팀장, 고객 담당자가 1~2분 안에 읽고 결론을 알 수 있어야 한다.

- 파일명: 프로토콜과 같은 이름에 `_report`를 붙인다. 예: `..._v3.md` → `..._v3_report.md`
- 프로토콜을 고쳐 새 버전을 만들면 보고서도 그 버전으로 새로 만든다.
- 대시보드 웹(`web/`)이 아래 제목과 `**판정**` 줄, 1장 표를 읽는다. **제목, 장 번호, 표 열 순서를 바꾸지 않는다.**

## 작성 원칙
- 새 사실을 만들지 않는다. 모든 내용은 프로토콜 본문에서 가져오고, 근거 칸에 본문 위치(장·FM#·DVP#)를 적는다.
- 문장은 짧게 쓴다. 한 칸에 한두 줄을 넘기지 않는다. 출처 태그는 근거 칸에만 둔다.
- **고객 요구값의 출처를 반드시 적는다.** 고객 문서에서 받은 값은 `고객: 문서명`, 법규는 `법규: 조문`, 우리가 정한 값은 `[가정]`이라고 쓴다. 가정이 많으면 결론 문단에 그렇게 밝힌다.
- 판단 기호는 넷 중 하나만 쓴다.
  - `✅ 가능`: 근거상 맞출 수 있음
  - `⚠ 위험`: 맞출 수도 있지만 시험이나 공정 개선이 필요함
  - `❌ 어려움`: 근거상 맞추기 어려움. 목표 재협의나 구조 변경이 필요함
  - `❓ 미확인`: 판단할 근거가 없음
- 판정은 셋 중 하나만 쓴다.
  - `진행`: ❌가 없고, ⚠는 계획된 시험으로 해소 가능
  - `조건부 진행`: ❌나 큰 ⚠가 있지만 조건(목표 재협의, 구조 변경 등)을 걸면 진행 가능
  - `보류`: 핵심 요구를 맞출 방법이 보이지 않음

## 형식

```markdown
# <부품명> 개발 계획 보고서

| 항목 | 내용 |
|---|---|
| 고객 / 요청 | <고객사> / <요청 내용 한 줄> (고객 문서가 없으면 "고객 요청 문서 없음 — 요구값은 [가정]") |
| 제품 / 적용 | <제품군> / <산업> <부품> |
| 개발 단계 | <개념 / 시제품 / 양산 전> |
| 기준 문서 | <프로토콜 파일명> |
| 작성일 | YYYY-MM-DD |

## 결론
**판정**: <진행 | 조건부 진행 | 보류>

<2~3문장: 무엇이 되고 무엇이 안 되는지, 진행 조건이 무엇인지>

## 1. 고객 요구 대비 대응 가능성
| 고객 요구 | 요구값 | 요구 출처 | 판단 | 이유 | 근거 |
|---|---|---|---|---|---|
| <항목> | <수치·조건> | <고객: 문서 / 법규: 조문 / [가정]> | <✅ 가능 / ⚠ 위험 / ❌ 어려움 / ❓ 미확인> | <한 줄> | <본문 위치> |

## 2. 검증 계획 요약
- 시험 <n>건 (사내 <n> · 외부/공인 <n>), 기간 <M1~Mn, 날짜>
- 이후 고객 승인 절차와 예상 기간

| 단계 | 기간 | 핵심 시험 | 이 단계 끝에 판단할 것 |
|---|---|---|---|
| <1차> | <M1> | <시험명 (DVP#)> | <진행/중단 판단 기준> |

## 3. 고객에게 받아야 할 것
1. <문서·정보> — <왜 필요한지>

## 4. 내부 결정 사항
1. <결정할 것> — <선택지>, <언제까지>

## 5. 주요 리스크
| 리스크 | 영향 | 대응 |
|---|---|---|
| <리스크> | <영향> | <대응·관련 DVP#> |
```
